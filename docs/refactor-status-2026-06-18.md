# 小墨匣架构瘦身收口记录（2026-06-18）

## 1. 当前结论

小墨匣的架构瘦身已经从“必须救火”阶段进入“够用就停”阶段。

当前不建议继续开新的“瘦身专项”。后续只做“功能驱动型抽取”，不要为了减少行数而继续拆文件、拆函数、拆状态。

现在更重要的是产品闭环，而不是继续追求代码体积变小。下一阶段应优先关注：

* 章节目录 / 阅读页体验
* 素材池参与生成
* `usedEventCards` 追溯

换句话说，当前项目更缺的是长篇小说工作台的真实使用闭环，不是更多抽象层。

## 2. 后端瘦身状态

后端已经完成了一轮主要整理，重点方向包括：

* 原子写入与 storage service
* Session / CORS 安全加固
* auth routes 抽离
* 编辑记忆相关逻辑整理
* 章节元数据相关逻辑整理
* 项目上下文文件 helper 整理
* variants / 候选版本 helper 整理

`server/index.js` 可能仍然不完美，也不会因为一次整理就变成理想架构，但它已经从高风险状态进入可维护状态。当前继续追求“拆得更细”收益很低，反而容易增加理解成本和回归风险。

不建议继续机械拆 `safeProjectDir`、`callDeepSeek`、`ensureDir` 这类底层小 helper。它们虽然仍在主文件附近，但承担的是基础能力，稳定、直接、可读，比为了减少行数而迁移更重要。

后端以后只在新增功能或修 bug 时顺手整理。整理必须服务于具体功能边界，而不是服务于文件行数。

## 3. 前端瘦身状态

前端当前不是完全瘦完的状态，`App.jsx` 仍然偏大。

但前端已经具备继续演进的骨架：

* 已经有 `DesktopApp` / `MobileApp` 壳层
* 已有移动端页面组件
* 已经出现桌面 / 移动端状态分层迹象
* 已抽出 `useReadingStateController`
* 最近移动端主路径修正是在不改生成链路、不改数据结构的前提下完成的

这说明前端已经从“所有东西都挤在一起”进入“可以按边界继续演进”的阶段。

当前不建议为了行数继续大拆 `App.jsx`。`App.jsx` 后续应该按功能边界逐步抽 controller / hook，而不是一次性重构。只有当某个产品功能需要更清晰的状态边界、事件边界或页面边界时，才进行小刀式整理。

## 5. 不建议继续做的事

当前不建议继续做以下事情：

* 不要继续机械拆 `App.jsx`
* 不要继续机械拆 `server/index.js`
* 不要为了减少行数拆 `safeProjectDir` / `ensureDir` / `callDeepSeek`
* 不要在没有功能目标的情况下重构移动端状态
* 不要大规模重写桌面端 UI
* 不要引入数据库
* 不要引入 TypeScript
* 不要引入复杂状态管理库
* 不要因为“看起来胖”就改动稳定链路
* 不要把瘦身任务直接交给 DS 继续狂拆 `master`

这些动作都可能制造新的不确定性，却不一定带来同等价值。现阶段最重要的是让产品能力继续往前走。

## 6. 后续允许的整理方式

后续只允许“功能驱动型抽取”。

可以接受的整理方式示例：

* 做素材池参与生成时，可以抽 `materialSelectionController` 或相关 hook
* 做章节目录 / 阅读页体验时，可以抽 `chapterNavigationController`
* 做项目设置优化时，可以抽 `projectSettingsController`
* 做生成状态增强时，可以抽 `generationController`
* 做移动端阅读增强时，可以继续沿 `useReadingStateController` 扩展

整理原则：

* 每次只抽一个边界
* 每次改完都要执行 `npm run build`
* 涉及生成链路时要跑 `generateStream` / `regenerateStream` 测试
* 不要在同一个 commit 里同时重构和改产品功能
* 不要直接大改 `master`
* 复杂前端拆分建议开分支，并优先使用 Claude Sonnet

理想节奏是：先有明确功能目标，再识别阻碍这个功能演进的代码边界，最后只抽那个边界。

## 7. 下一阶段建议优先级

建议下一阶段按以下优先级推进：

1. 章节目录 / 阅读页体验优化
2. 素材池参与章节生成
3. `usedEventCards` 使用追溯
4. 灵格工坊事件卡导入
5. 小说反馈卡
6. 长篇项目结构增强

当前项目更缺产品闭环，不缺抽象层。

下一阶段应该从“代码瘦身”转向“长篇小说工作台能力建设”。代码整理仍然可以做，但必须作为产品能力建设的一部分出现。

## 8. 当前停止点

从 2026-06-18 起，小墨匣不再继续进行单独的“瘦身专项”。

后续原则：

* 后端：停止主动拆分，只做功能驱动整理。
* 前端：停止大拆 `App.jsx`，只做小刀式 controller / hook 抽取。
* 移动端：保持现有路径稳定，先观察实际使用反馈。
* `master`：保持稳定，不做无目标重构。

这个停止点不是说代码已经完美，而是说继续“为瘦身而瘦身”已经不再是当前最优解。
